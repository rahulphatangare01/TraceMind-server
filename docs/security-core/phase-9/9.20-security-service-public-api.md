# Phase 9.20 — Security Service Public API Documentation

## 1. Purpose

The Security Service provides a stable application-facing API for cryptographic operations in TraceMind.

Business modules must use the Security Service instead of directly accessing low-level cryptographic providers, raw key material, or Node.js cryptographic APIs.

The Security Core is designed to keep cryptographic implementation details separate from business logic.

## 2. Architecture

```text
TraceMind Business Modules
           |
           v
    SecurityService
           |
           v
    SecurityServiceFacade
           |
           +-- Request Validation
           +-- Security Context Validation
           +-- Security Boundary Validation
           +-- Operation-specific APIs
           +-- Error Handling
           |
           v
    Provider / Key Dependencies
           |
           v
    Local Security Provider
```

The facade provides one entry point for the eight supported public cryptographic operations.

Provider resolution and key management remain separate Security Core capabilities.

## 3. Public API Contract

The public contract is defined by:

`src/modules/security-core/application/interfaces/security.service.interface.ts`

The `SecurityService` interface exposes these methods:

| Method                     | Purpose                                                                |
| -------------------------- | ---------------------------------------------------------------------- |
| `encrypt(request)`         | Encrypt plaintext using the configured security dependencies.          |
| `decrypt(request)`         | Decrypt ciphertext using the supplied encryption metadata and context. |
| `hash(request)`            | Generate a hash using the requested algorithm.                         |
| `verifyHash(request)`      | Verify a value against a supplied hash.                                |
| `sign(request)`            | Sign a payload using the requested signature algorithm.                |
| `verifySignature(request)` | Verify a payload signature.                                            |
| `createHmac(request)`      | Generate an HMAC for a payload.                                        |
| `verifyHmac(request)`      | Verify an HMAC for a payload.                                          |

All eight methods return promises with their respective result types.

### 3.1 Encryption

Request type: `EncryptRequest`

Fields:

- `plaintext`: string to encrypt.
- `context`: security context for the operation.
- `keyId`: identifier of the key to use.
- `encoding`: optional output encoding.

Result type: `EncryptResult`

Fields:

- `ciphertext`
- `algorithm`
- `encoding`
- `iv`
- `authTag`
- `keyId`
- `keyVersion`

The encryption result includes the metadata required by the existing decryption contract. Raw key material must not be returned.

### 3.2 Decryption

Request type: `DecryptRequest`

Fields:

- `ciphertext`
- `algorithm`
- `encoding`
- `iv`
- `authTag`
- `keyId`
- `keyVersion`
- `context`

Result type: `DecryptResult`

- `plaintext`

The caller must supply the required encryption metadata and an appropriate security context.

### 3.3 Hashing

Request type: `HashRequest`

Fields:

- `value`
- `algorithm`
- `encoding` (optional)

Result type: `HashResult`

- `hash`
- `algorithm`
- `encoding`

### 3.4 Hash Verification

Request type: `VerifyHashRequest`

Fields:

- `value`
- `hash`
- `algorithm`
- `encoding` (optional)

Result type: `VerifyHashResult`

- `valid`: boolean indicating whether verification succeeded.

### 3.5 Signing

Request type: `SignRequest`

Fields:

- `payload`
- `algorithm`
- `context`
- `encoding` (optional)

Result type: `SignResult`

- `signature`
- `algorithm`
- `encoding`
- `keyId`
- `keyVersion`

Private signing keys must not be exposed through the public API.

### 3.6 Signature Verification

Request type: `VerifySignatureRequest`

Fields:

- `payload`
- `signature`
- `algorithm`
- `keyId`
- `keyVersion`
- `context`
- `encoding` (optional)

Result type: `VerifySignatureResult`

- `valid`: boolean indicating whether verification succeeded.

### 3.7 HMAC Creation

Request type: `CreateHmacRequest`

Fields:

- `payload`
- `algorithm`
- `context`
- `encoding` (optional)

Result type: `CreateHmacResult`

- `signature`
- `algorithm`
- `encoding`
- `keyId`
- `keyVersion`

HMAC key material must remain inside the appropriate Security Core dependencies.

### 3.8 HMAC Verification

Request type: `VerifyHmacRequest`

Fields:

- `payload`
- `signature`
- `algorithm`
- `keyId`
- `keyVersion`
- `context`
- `encoding` (optional)

Result type: `VerifyHmacResult`

- `valid`: boolean indicating whether verification succeeded.

## 4. Security Context

The security context identifies the scope, tenant boundary, data classification, and purpose of a security operation.

The context contract includes:

```ts
interface SecurityContext {
  scope: SecurityScope;
  organizationId?: string;
  projectId?: string;
  applicationId?: string;
  environmentId?: string;
  classification: DataClassification;
  purpose: SecurityPurpose;
}
```

The actual interface in the source code is authoritative.

### 4.1 Supported scopes

| Scope          | Intended boundary                                                |
| -------------- | ---------------------------------------------------------------- |
| `PLATFORM`     | Platform-level operations.                                       |
| `ORGANIZATION` | Organization-level operations.                                   |
| `PROJECT`      | Project-level operations.                                        |
| `APPLICATION`  | Application-level operations.                                    |
| `ENVIRONMENT`  | Environment-level operations.                                    |
| `FIELD`        | Reserved field-level scope governed by the existing scope rules. |

### 4.2 Context validation flow

```text
Operation Request
       |
       v
Request Validation
       |
       v
SecurityContextValidator
       |
       v
SecurityBoundaryValidator
       |
       v
Operation-specific processing
```

The validators enforce the existing schema, identifier, and hierarchy rules.

Invalid scopes, missing required identifiers, forbidden identifiers, and invalid hierarchy combinations must be rejected.

The boundary validator normalizes supported context fields and returns the normalized context. Callers should use the validated context rather than bypassing validation.

Hashing and hash verification use their existing request contracts and do not require a `SecurityContext` field.

## 5. Provider Resolution

Provider resolution is an internal Security Core capability.

The application-facing service should not depend on a particular provider implementation.

Provider-specific behavior must remain behind the established provider interfaces and resolution services.

Rules:

- Do not silently fall back to another provider when resolution fails.
- Preserve the existing provider-resolution error behavior.
- Do not register cryptographic operation providers as general `SecurityProvider` instances unless their contracts explicitly require it.
- Do not expose provider internals to business modules.

## 6. Key Management

Key management is separate from the eight-operation `SecurityService` facade.

The existing key management API supports metadata-oriented operations such as:

- Creating a key.
- Retrieving key metadata.
- Retrieving a key version.
- Retrieving the active key version.
- Rotating a key.
- Changing a key version's status.

The exact available methods and request contracts are defined by the existing `KeyProvider` and `SecurityServiceKeyManagementApi` interfaces and implementations.

Security rules:

- Do not return raw key material.
- Do not expose private signing keys.
- Preserve key identity and version metadata.
- Keep key operations behind the existing Security Core abstractions.
- Do not add unimplemented key export or raw-key retrieval operations to the public API.

## 7. Error Handling

The facade uses `SecurityServiceErrorHandlingService` to apply the established error-handling policy.

Expected behavior:

- Preserve recognized Security Core errors.
- Preserve context and boundary validation errors.
- Convert unexpected errors to a generic Security Core error.
- Avoid exposing sensitive input values through generic error messages.
- Do not introduce a parallel error hierarchy unnecessarily.

Consumers should handle expected operation failures without depending on internal provider implementation details.

## 8. Usage Example

The following example demonstrates the public API shape. Import paths may vary depending on the consuming module.

```ts
import { securityCore } from "./security-core.container.js";

const securityService = securityCore.securityService;

const hashResult = await securityService.hash({
  value: "example payload",
  algorithm: HashAlgorithm.SHA_256,
  encoding: CryptoEncoding.HEX,
});

const verificationResult = await securityService.verifyHash({
  value: "example payload",
  hash: hashResult.hash,
  algorithm: HashAlgorithm.SHA_256,
  encoding: CryptoEncoding.HEX,
});

if (!verificationResult.valid) {
  throw new Error("Hash verification failed");
}
```

The example assumes `HashAlgorithm` and `CryptoEncoding` are imported from the project's existing domain enums.

Consumers should use the configured Security Core instance rather than constructing providers directly.

## 9. Security Boundaries

The following architectural rules apply to business modules.

### Allowed

- Calling the public `SecurityService`.
- Supplying validated operation requests.
- Supplying the appropriate security context for context-bearing operations.
- Handling public result types and expected errors.

### Not allowed

- Calling Node.js crypto APIs directly from business modules for operations managed by Security Core.
- Accessing `LocalCryptoProvider` directly from business modules.
- Accessing raw key material providers.
- Returning raw key material or private signing keys to business code.
- Bypassing security context and boundary validation.
- Silently falling back when provider resolution fails.
- Logging plaintext secrets, credentials, private keys, or sensitive cryptographic material.

Encryption does not replace authorization. Authorization and tenant-access decisions remain responsibilities of the appropriate access-control layer.

## 10. Testing and Regression

The Phase 9 test suite should cover:

- Public API contract and method availability.
- Encryption and decryption behavior.
- Hashing and hash verification.
- Signing and signature verification.
- HMAC creation and verification.
- Security context and boundary validation.
- Provider resolution behavior.
- Key management contract compatibility.
- Error preservation and sanitization.
- Container wiring and existing API compatibility.

Use the project's existing test commands and test configuration. Do not treat a documentation example as proof that a security operation has passed runtime verification.

## 11. Known Limitations

Documented behavior must match the current implementation.

In particular:

- Local provider capabilities and persistence limitations must be described accurately.
- Provider fallback must not be implied where none exists.
- Signature context binding must not be claimed unless the implementation cryptographically enforces it.
- Future cloud KMS integrations must not be described as implemented until they are available and verified.
